# Agent 对话持久化与跨会话长期记忆

## Goal

为后续 Agent 对话界面提供可跨天恢复的永久会话历史，并从完成的文本
对话中异步提炼可跨会话召回的 Mem0 风格用户长期记忆。Redis LangGraph
checkpoint 继续只负责活动 DDL 任务恢复，不承担对话历史职责。

## Background

- 当前 MySQL `data_agent.agent_memory`、只追加事件、记忆关联和索引
  outbox 已构成 Mem0 风格长期记忆权威层；Elasticsearch 与 Qdrant
  是可重建检索投影。
- 当前长期记忆内容仅覆盖 DDL 表列语义、指标问题、用户回答和指标定义，
  没有 `user_id`、会话、消息、摘要或对话历史 API。
- Redis checkpoint 默认保留 24 小时，保存 LangGraph 节点、路由、
  interrupt、重试和校验状态；终态后会被清理。
- 未来对话产品需要一个用户拥有多个独立会话，并在新会话中召回该用户
  已明确表达的事实、偏好、约束和业务规则。

## Requirements

### R1. 会话与消息权威存储

- MySQL 永久保存会话、`user`/`assistant` 纯文本消息、稳定顺序和时间，
  直到用户主动删除。
- 一个 `user_id` 可以拥有多个会话；原始消息只能在所属用户和会话内读取。
- 会话历史使用稳定游标分页，不能依赖 Redis TTL、offset 快照或派生索引。
- 首版明确拒绝附件、非文本载荷和其他消息角色，不能静默丢弃内容。

### R2. 对话轮次与幂等

- 同一轮用户输入、助手响应和长期记忆提炼 outbox 使用稳定 `turn_uid`
  幂等关联。
- 用户消息先持久化；只有助手消息与提炼 outbox 成功提交后，本轮才可以
  向调用方报告完成。
- 重试同一 `turn_uid` 不得产生重复用户消息、助手消息或提炼任务。
- 同一会话首版只允许一个在途轮次，避免并发上下文顺序不确定。

### R3. 异步 Mem0 风格提炼

- 完成一轮对话后，由现有 arq worker 从 MySQL outbox 异步提炼长期记忆；
  对话响应不等待记忆提炼、TEI、Elasticsearch 或 Qdrant。
- 提炼器可读取完整轮次和有界上下文，但只有用户明确表达的身份、偏好、
  约束、业务规则，以及用户后来明确确认的助手结论可以成为长期记忆。
- 助手单方面的建议、猜测、推断、模糊确认和未验证模型输出不得进入长期记忆。
- 提炼候选必须携带可由代码校验的用户原文证据和消息标识；Prompt 不能成为
  唯一可信边界。
- 提炼失败保留 outbox 并有界退避重试，不能回滚或隐藏已经持久化的消息。

### R4. 长期记忆与用户隔离

- 复用现有 MySQL 权威记忆、事件、关联、内容哈希、软删除、索引 outbox、
  ES/Qdrant 混合召回和 MySQL 回查，不创建第二套通用记忆栈。
- 对话长期记忆增加明确 `user_id` 和会话/消息来源；所有权威读取、索引
  查询、回查、更新和删除必须在数据库或索引查询中强制过滤 `user_id`。
- 同一用户的长期记忆跨会话共享；不同用户之间不得串读。
- 长期记忆默认永久保留，并支持独立的查询、历史、修正和删除。

### R5. 有界上下文

- 模型上下文由当前会话摘要、摘要之后的最近有界消息、与当前输入相关的
  同用户长期记忆和当前输入组成。
- 完整原始历史只在 MySQL 中分页读取；首版不为每条消息建立独立向量索引。
- 摘要异步更新并记录覆盖到的消息游标；摘要失败或滞后不能阻塞聊天，
  上下文必须安全回退到有界原始消息。

### R6. 删除语义

- 删除会话时删除该用户在该会话中的消息和待提炼 outbox，不自动删除已经
  跨会话共享的长期记忆。
- 删除单条长期记忆沿用可审计软删除和 ES/Qdrant DELETE outbox。
- 删除用户时立即让该用户的会话和长期记忆不可召回，删除会话/消息，
  tombstone 长期记忆并投递派生索引删除；两个索引删除确认后再物理清理
  被标记为用户级清除的权威记忆与历史。

### R7. 产品和安全边界

- 本任务交付后端 API、持久化、上下文组装、异步提炼与召回，不实现聊天 UI。
- 首版只有一个 Data Agent，不增加 `agent_id` 或 Agent 管理表。
- 本任务不实现认证；API 继续仅监听 `127.0.0.1`，`user_id` 由未来可信
  认证层提供。服务开放到局域网或公网前必须先接入鉴权。
- 不保存隐藏思维链、完整 Prompt、凭据、附件或无界模型响应。

### R8. 兼容、迁移与恢复

- Redis job、LangGraph checkpoint、DDL 工作流和现有 DDL 长期记忆语义保持不变。
- 新会话表、记忆租户/来源字段和索引字段同时更新 SQLAlchemy Core 定义、
  新环境 bootstrap SQL；`docs/docker/mysql/` 只保留创建语句，不提供
  `ALTER TABLE`、数据更新或已初始化环境升级脚本。
- 记忆投影版本升级后显式重建项目专用 ES index 和 Qdrant collection；
  旧投影不得进入用户记忆召回。
- 不新增 Mem0 SDK、另一个任务队列、ORM 或数据库迁移框架。

## Acceptance Criteria

- AC1（R1）：清理 Redis checkpoint 并经过 24 小时后，仍能按
  `user_id + conversation_uid` 游标分页读取完整、顺序稳定的文本消息。
- AC2（R1、R4）：同一用户的多个会话时间线彼此独立并共享长期记忆；
  其他 `user_id` 对会话、消息游标、记忆 UID、搜索、历史、修正和删除
  均得到不可见结果。
- AC3（R2）：重复提交同一 `turn_uid` 最终只有一条用户消息、一条助手消息
  和一条提炼 outbox；助手消息持久化失败时不得报告轮次完成。
- AC4（R3）：长期记忆提炼或 LLM/TEI/ES/Qdrant 故障时消息仍可读取，
  outbox 保留并可重试成功。
- AC5（R3）：明确用户事实可以成为长期记忆；助手单方面猜测和模糊确认被
  拒绝；用户后续明确确认的助手结论可以被接受。
- AC6（R4）：用户长期记忆写入 MySQL 权威层并通过现有 ES/Qdrant
  混合召回；所有索引结果均按 `user_id` 回查 MySQL 后才能进入上下文。
- AC7（R5）：长会话上下文始终受配置的消息数、字符数和摘要长度限制，
  同时包含可用摘要、最近消息、相关同用户长期记忆和当前输入。
- AC8（R6）：删除会话不会删除共享长期记忆；删除用户后其数据立即不可
  召回，派生索引删除可重试并最终完成权威清理。
- AC9（R7）：未知字段、空文本、超长文本、附件、多模态载荷和非
  `user`/`assistant` 角色在 HTTP/Pydantic 边界被明确拒绝。
- AC10（R8）：现有 DDL interrupt/resume、checkpoint 清理、Meta 快照、
  DDL 长期记忆和索引 outbox 测试保持通过。
- AC11（R8）：新环境 bootstrap 与已初始化环境升级都得到相同表结构；
  投影版本升级和显式重建后不存在旧的无租户索引文档。
- AC12（全部）：Ruff、Pyright、compileall、配置加载、非集成测试及可用的
  MySQL/Redis/ES/Qdrant/TEI 集成检查通过；未运行的外部能力探针如实报告。

## Out of Scope

- 可视化聊天界面。
- 登录、账号、Token 和权限管理。
- 多 Agent 注册、配置与 Agent 间记忆隔离。
- 附件、对象存储、表格、图片、多模态内容和 OCR。
- 每条历史消息的向量索引或会话内语义搜索。
- Mem0 托管平台闭源排序、时间推理、自动衰减或直接引入 Mem0 SDK。
