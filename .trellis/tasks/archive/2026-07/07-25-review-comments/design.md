# 审查设计

## 审查边界

本任务先对当前 `origin/master` 快照进行全仓注释语义审查，再对确认的核心业务流程补充中文解释性注释。修改只触及注释、Docstring 和维护备注，不改变可执行语句。

审查分为六个互不重叠的分区：

1. 配置与基础设施：`settings.py`、`infrastructure/**`、`conf/**`、`pyproject.toml`、CI 和 Docker。
2. 对话域：`conversation/**` 及对应测试。
3. DDL 任务与工作流：`ddl_metadata/jobs/**`、`workflow/**`、解析与对应测试。
4. 长期记忆：`ddl_metadata/memory/**`、`models/memory.py` 及对应测试。
5. 其他运行时与测试模块：上述分区未覆盖的 `src/**` 和 `tests/**`。
6. Schema 与现行说明：`docs/docker/mysql/**`、根级现行说明文件和运行备注。

实施阶段聚焦三个可读性分区：

1. DDL 任务与工作流：任务受理、事务/outbox、调度、checkpoint、interrupt/resume、失败重试和终态清理。
2. Conversation 生命周期：消息持久化、单活动 turn、摘要游标、删除/purge 顺序与用户记忆抽取边界。
3. 长期记忆：用户级与 DDL 级作用域、更新/删除事务边界、搜索权威回查、索引 outbox 和生命周期判定。

## 审查数据流

1. 使用 AST/tokenize 和关键字搜索生成确定性清单，确认每个文件只落入一个分区。
2. 分区审查代理逐个核对 Docstring/注释与同文件实现、直接调用方和对应测试，输出候选问题及 `file:line` 证据。
3. 主会话按候选证据做定点复核，排除纯偏好、Ruff 已覆盖的格式噪声和无法证明的猜测。
4. 独立检查代理复核全范围覆盖、规范符合性和报告证据。
5. 聚合为中文报告，区分确认问题、维护建议、无问题区域、排除项和验证限制。
6. 在定位清单通过评审后，由实施代理仅修改获准的注释/Docstring；主会话定点核验 diff 与实现。
7. 使用 AST 结构对比确认注释修改前后可执行结构一致，再运行 Ruff、Pyright 和相关测试。

## 判定契约

- **语义错误**：注释或 Docstring 与当前实现、签名、调用契约、异常、副作用、事务、并发或生命周期事实矛盾。
- **过期备注**：备注引用的版本、约束或移除条件与当前仓库事实不一致；外部状态无法离线验证时只标候选。
- **误导性遗漏**：公共复杂对象省略了会显著影响正确使用的非显然约束，且相关约束能由代码路径证明。
- **占位/冗余**：只复述名称或可见语句，未表达契约、理由或不变量；默认属于非阻塞维护问题。
- **有效注释**：解释 rationale/invariant、准确业务契约或必要工具抑制，不因语言简短而误报。
- **SQL COMMENT**：按字段/表契约与模型和仓储一致性判断，不适用普通 Docstring 风格要求。

## 证据与严重程度

- 每个候选问题必须包含一个根因、准确行号、触发或误用条件、可观察后果和最小修复方向。
- `P0/P1` 严格按 `code_review.md` 评估，不把格式、措辞或普通维护债务升级为阻塞问题。
- 非阻塞项按用户确认的口径进入最终报告，必须显式标记为“维护建议”，不得伪装为 P0/P1。

## 风险控制

- 并行分区防止遗漏，但最终候选由主会话定点复核，避免代理猜测直接进入报告。
- 扫描工具只用于清单与格式信号，不替代语义核验。
- 外部依赖版本事实只使用官方来源核验，并单独记录来源和日期。
- 每组相邻语句最多使用一条能够解释共同不变量的注释；相同事实不在 API、service、repository 三层重复陈述。
- 运行时行为由修改前后 AST 结构对比保护；任何可执行结构差异都视为失败。
- 注释修改与任务产物位于独立 worktree；若注释质量检查失败，只回滚本任务明确修改的注释，不触碰用户原工作区。
