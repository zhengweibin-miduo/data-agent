# 让 Codex 自主判断受干预分支能否安全提交推送

## Goal

让本地 Codex 和仓库 GitHub 委派任务在同一 PR 分支受到其他 Codex
任务或协作者干预时，基于可验证的 Git 历史关系判断能否安全继续提交和
推送，而不是看到远端 head 变化就一律停止。

## Requirements

- 继续遵守显式授权边界：只有用户指令或已授权工作流已经包含 commit /
  push 时，Codex 才能执行对应操作；本改动不得把“修改代码”扩大为推送授权。
- 每次依赖远端状态作决定前必须 fetch，并记录本地任务基线、当前本地
  HEAD、远端 PR head 和待提交文件范围。
- 对远端线性前进、仅存在本任务未发布提交、真正历史分叉、工作区冲突和
  未识别改动做出不同决策；允许安全情况自动收敛，危险情况必须停止。
- 自动收敛只能使用保持远端历史的操作：`merge --ff-only`，或只重放
  已核验为本任务且从未发布的本地提交。不得 rebase 已共享提交，不得
  reset 用户工作，不得 stash 未经授权的改动。
- 普通 push 必须依赖服务端 fast-forward 检查处理最终竞态；远端再次
  前进时重新 fetch 和判定，不得用 force / force-with-lease 绕过。
- Codex 自主继续前必须重新核验提交范围、远端新增提交和相关验证结果；
  出现冲突、未知提交来源或范围、无法证明祖先关系、需要改写共享历史时停止。
- 更新 Trellis Phase 3.4，使已有 commit / push 授权可以一次确认后执行，
  同时保留未授权场景的一次性确认。
- GitHub 的审查修复、CI 修复和冲突处理委派必须读取同一项目规则，并从
  “head 变化即停止”改为按上述判定矩阵处理。
- 不创建新 PR，不改变 PR base/head，不 force-push。

## Acceptance Criteria

- [x] 项目 Git/PR Skill 明确定义授权门禁、远端干预判定矩阵、允许动作、
  停止条件和竞态处理。
- [x] Trellis Phase 3.4 在已有授权且所有安全门禁通过时允许直接提交并推送；
  无授权时仍要求确认，且 unrecognized dirty files 不会被静默包含。
- [x] 远端 PR head 是本地任务基线的线性后继且本地只有本任务改动时，
  Codex 可同步、重新验证并正常推送。
- [x] 本地只有未发布的本任务提交时，可在最新远端之上安全重放这些提交，
  不改写任何已发布历史。
- [x] 历史真正分叉、发生冲突、存在未识别改动、无法确定提交归属或只能
  强推时，Codex 明确停止并报告原因。
- [x] 三个 GitHub 委派提示词均引用项目 Git/PR 规则并采用相同判定语义。
- [x] 委派脚本自测覆盖“远端线性前进可继续”和“危险状态必须停止”的提示词约束。
- [x] 相关格式检查和测试通过，最终提交只包含本任务文件并推送到 PR #71
  原 head 分支，不新建 PR、不 force-push。

## Notes

- “直接提交推送”表示不因可安全吸收的线性远端更新而额外打断用户，不表示
  跳过最初授权、范围检查、验证或 Git 的 fast-forward 保护。
- 本任务直接修改项目工作流和项目级 Git/PR Skill；该知识已落在权威规则
  文件中，不需要再复制到 backend / frontend code-spec。
