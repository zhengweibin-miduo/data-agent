# 归纳 Data Agent 项目技术架构设计

## Goal

基于当前 `data-agent` 仓库的真实代码、配置、数据库脚本、部署资源和测试，编写一套面向个人项目维护的技术架构设计归纳文档。文档应准确解释项目目标、系统边界、模块职责、运行时数据流、存储模型、关键技术选型、可靠性机制和部署结构，帮助作者快速回顾设计并支持后续演进。

## Background

- 这是当前项目的架构设计归纳，不是通用软件架构知识库，也不使用虚构案例。
- 当前项目是 Python 3.13 后端应用，核心依赖包括 FastAPI、arq、LangGraph、MySQL、Redis、Elasticsearch、Qdrant、Hugging Face TEI 和 OpenAI 兼容模型接口。
- 当前主要业务能力是：接收 MySQL DDL，解析物理模式，调用 LLM 生成并校验语义元数据与指标，必要时中断等待用户回答，再持久化元数据和长期记忆。
- API 进程与 worker 进程职责分离；Redis 承担任务状态、调度、租约与 LangGraph 检查点，MySQL 承担元数据快照和长期记忆持久化。
- `docs/docker/` 已提供 MySQL、Redis、Elasticsearch、Qdrant 和 TEI 的本地基础设施配置。
- 文档借鉴 arc42 的项目架构关注点、C4 的分层视图和 ADR 的决策记录方式，但内容必须来自本项目事实。

## Requirements

### R1. 项目概览与系统边界

说明项目解决的问题、目标用户、当前能力、外部参与者、外部系统以及明确不承担的职责。

### R2. 架构视图

至少提供以下中文架构信息图：

- 系统上下文图。
- 容器/进程与基础设施关系图。
- 核心模块/组件关系图。
- DDL 元数据任务主流程图或时序图。
- LangGraph 工作流图。
- 关键数据或部署关系图。

### R3. 模块职责

基于实际目录和代码说明：

- FastAPI 应用组合与 HTTP API。
- DDL 解析、模型、校验与错误体系。
- LangGraph 工作流及人工介入。
- arq worker、重试、调度和清理。
- 任务状态存储与长期记忆服务。
- MySQL 持久化仓储。
- Redis、LLM、Qdrant、Elasticsearch 和 TEI 基础设施适配层。
- 配置、日志与测试结构。

### R4. 运行时数据流

准确归纳任务提交、异步分发、工作流执行、用户回答恢复、结果投影、持久化和检查点清理的完整路径，并说明关键状态与失败分支。

### R5. 数据与状态

说明 MySQL 数据库职责、Redis 键与状态职责、LangGraph 检查点、元数据模型、长期记忆、任务修订和来源租约之间的关系。数据结构只引用或归纳真实实现。

### R6. 质量属性与可靠性

结合现有实现说明：

- 异步处理与并发边界。
- 幂等、修订校验和来源租约。
- 重试、失败分类和安全错误投影。
- 结构化输出与确定性校验。
- 检查点恢复与人工介入。
- 数据持久化、清理和保留策略。
- 测试层次及已验证边界。

### R7. 技术选型与架构决策

归纳项目中能够从代码或配置证明的关键决策及其权衡，例如 FastAPI、arq、LangGraph、Redis、MySQL、结构化 LLM 输出和本地基础设施。无法由仓库证明的动机必须标记为推断或待确认，不得写成既定事实。

### R8. 文档格式

- 使用中文 HTML。
- 借鉴参考文章 `https://linux.do/t/topic/2571606` 的长文组织方式：目录导航、分层标题、重点引用块、章节分隔和穿插式大幅信息图；不得复制其正文。
- 所有系统上下文、进程、模块、数据、部署和 To-Be 架构图转换为实际可见的中文 SVG 图片，不再把 Mermaid 或 ASCII 代码块作为最终图表。
- 图表以“组件、关系、分支条件”的阅读顺序直接表达，不使用需要额外对照的组件编号。
- 页面需适配桌面与移动端，并提供打印样式。
- 代码、SQL 和 YAML 只摘录解释架构所需的短片段，不复制大段实现。
- 提供清晰入口、目录导航、文档范围、事实来源和维护约定。

### R9. 项目归纳原则

- 每个架构结论必须能够追溯到代码、配置、数据库脚本、测试或项目规范。
- 当前实现、推断、风险和未来建议必须明确区分。
- 不为填充章节而引入项目中不存在的通用架构主题。
- 不创建与当前项目无关的系统案例或架构百科内容。

### R10. 当前与目标架构

- 文档主体描述仓库当前已经实现的架构（As-Is）。
- 单独设置风险、技术债与演进建议（To-Be）章节。
- 当前架构与目标架构不得混画或混写。
- 每项演进建议应说明触发条件、预期收益、代价或风险以及建议优先级。
- 尚未实现的能力不得描述为项目当前能力。

### R11. 交付形态

- 最终架构归纳采用单个中文 HTML 阅读入口，而不是模块化文档站点。
- 默认文件位置为 `docs/architecture.html`，图片资源放在 `docs/architecture-assets/`。
- 文档使用清晰的章节编号、目录和内部锚点保持长文档可导航。
- 项目根入口应能链接到该文档，但不把正文拆分到多个章节文件。
- HTML 不依赖在线 JavaScript 或 CSS 才能阅读；所有图片使用仓库内相对路径。

### R12. 实现校验

- 架构结论在编写过程中需要结合当前实现校验，但正文不展示实现依据、源码路径、测试路径或证据索引。
- 文档不提供实现依据清单或“架构结论—源文件”索引。
- 模块职责章节可保留理解架构所必需的模块名称，但不扩展为证据清单。

### R13. To-Be 技术架构范围

- To-Be 章节聚焦技术架构设计，不以产品化、商业化或运营能力为主线。
- 目标架构应从当前实现的技术约束、耦合、可靠性边界和演进需求出发。
- 重点讨论模块边界、依赖方向、进程职责、状态与数据职责、工作流执行、外部服务适配、可靠性、可测试性和部署拓扑。
- 认证、多租户、计费、运营后台等产品化能力除非直接影响当前技术边界，否则不纳入主要建议。
- To-Be 内容必须与 As-Is 清楚分隔，并说明从当前架构演进的理由。

### R14. 目标架构表达

- To-Be 章节给出一套明确推荐的目标技术架构，并提供对应中文 SVG 架构图。
- 对存在实质争议的关键设计点列出备选方案、适用条件与权衡，但最终给出推荐结论。
- 提供从 As-Is 到 To-Be 的分阶段演进路径。
- 每个演进阶段说明改造范围、技术收益、主要风险和验证方式。
- 目标架构作为后续技术设计基线，不代表本任务需要实施该架构。

## Acceptance Criteria

- [ ] 文档入口能够让读者快速理解项目目标、范围和整体技术栈。
- [ ] 系统上下文、进程/基础设施、核心组件、主流程和 LangGraph 工作流均有清晰的中文 SVG 信息图。
- [ ] 文档覆盖 API、worker、工作流、任务状态、记忆、持久化和基础设施适配层的真实职责。
- [ ] 一个 DDL 任务从提交到成功、等待输入、恢复或失败的路径能够完整追踪。
- [ ] MySQL、Redis、LangGraph 检查点及外部服务的数据职责被清楚区分。
- [ ] 可靠性、幂等、重试、校验、清理和错误处理均与现有实现一致。
- [ ] 技术选型事实、推断、风险和未来建议没有混写。
- [ ] HTML 中不包含 Mermaid 图或作为最终图表的 ASCII 代码块；所有图片链接有效且可见。
- [ ] 文档中的文件引用、接口路径、组件名称和配置项能在仓库中找到依据。
- [ ] `docs/architecture.html` 是唯一阅读入口，根 README 提供有效入口且不重复正文。
- [ ] To-Be 章节给出一套推荐技术架构、关键备选方案与分阶段演进路径，并与 As-Is 清楚分隔。
- [ ] 每项演进阶段说明改造范围、技术收益、风险和验证方式。
- [ ] 不包含虚构案例或与本项目无关的通用知识章节。

## Out of Scope

- 不建设独立在线文档站点或部署流水线。
- 不编写通用软件架构知识库。
- 不覆盖前端、移动端、嵌入式或其他与当前项目无关的架构领域。
- 不实现新的业务功能或改变现有运行行为。
- 不把外部项目的正文复制到本仓库。
