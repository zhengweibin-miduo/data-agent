# Data Agent 技术架构归纳文档设计

## 1. 交付边界

本任务只新增和维护架构文档，不改变应用代码、配置语义、数据库结构或运行行为。

主要交付物：

- `docs/architecture.md`：唯一的架构正文。
- `README.md`：增加项目简介和架构文档入口；当前文件为空，因此不会覆盖既有说明。

任务保持单一交付，不拆分子任务。虽然正文包含多个章节，但它们共享同一事实清单、术语和图例，独立拆分会增加交叉章节不一致风险。

## 2. 文档信息架构

`docs/architecture.md` 使用以下固定顺序：

1. 文档目的、范围、状态与阅读方式。
2. 项目目标、核心能力与约束。
3. 技术栈总览。
4. As-Is 系统上下文。
5. As-Is 进程与基础设施架构。
6. As-Is 代码模块与依赖方向。
7. HTTP API 与异步任务运行流程。
8. LangGraph DDL 元数据工作流。
9. 人工介入、恢复与修订机制。
10. MySQL、Redis、检查点和长期记忆的数据职责。
11. 可靠性、幂等、重试、错误投影和清理。
12. 配置、日志、部署和本地基础设施。
13. 测试架构与当前质量边界。
14. 已实现的关键架构决策及权衡。
15. 风险与技术债。
16. To-Be 推荐技术架构。
17. 关键备选方案对比。
18. 分阶段演进路径。
19. 术语表与“架构结论—源文件”索引。

## 3. 事实提取与内部校验模型

写作前建立内部事实清单，按以下类别审阅仓库：

| 类别 | 主要来源 |
|---|---|
| 应用组合与 API | `application.py`、`api.py`、`main.py` |
| 工作流 | `workflow/graph.py`、`workflow/metadata_generator.py` |
| 异步执行 | `worker.py`、`jobs/store.py` |
| 领域契约 | `models/`、`parsing.py`、`validation.py`、`errors.py` |
| 长期记忆 | `memory/`、`persistence/memory_repository.py` |
| 元数据持久化 | `persistence/tables.py`、`metadata_repository.py`、MySQL 脚本 |
| 外部依赖 | `infrastructure/`、`settings.py`、`app_config.yaml` |
| 部署 | `docs/docker/docker-compose.yml` 及镜像构建文件 |
| 质量边界 | `tests/`、`.github/`、`.trellis/spec/backend/` |

正文结论分为四种标签：

- **当前实现**：可由仓库直接证明。
- **推断**：从多个实现事实得出的解释，明确说明推断依据。
- **风险/技术债**：当前实现存在的约束或维护风险。
- **目标设计**：To-Be 推荐，不描述为已实现。

实现信息仅用于编写过程中的内部校验。读者正文不提供“实现依据”列表、源码路径、测试路径或主题到源文件的反向索引。

## 4. ASCII 拓扑图设计

所有架构图使用 ASCII 拓扑图格式，统一视觉和命名规则：

- 系统边界使用等宽方框和清晰标题。
- 人员、进程、存储和外部系统直接写入方框，不使用 `[P1]`、`[S1]` 等编号。
- 节点名称和分支说明使用中文，结构符号使用 ASCII 方框与箭头。
- 方框按中文字符的实际显示宽度补齐，连线按显示列定位，减少字体差异导致的错位。
- 保留拓扑、并行分支、状态转换和分层架构各自适合的原始结构。
- 关系箭头旁写明协议或数据含义，分支条件紧邻分叉点。
- As-Is 图标题或说明明确标识“当前架构”。
- To-Be 使用独立图，不在 As-Is 图上用虚线混入未来组件。
- 图中名称与代码模块、服务名、配置名一致。

## 5. As-Is 写作策略

As-Is 章节以运行路径为主线，不逐文件罗列：

1. FastAPI 接受 DDL 任务并把持久受理委托给 `DDLJobStore`。
2. Redis 原子维护任务、修订、来源租约和 dispatch outbox。
3. arq worker 拉取任务并构建或恢复 LangGraph。
4. 图执行确定性解析、记忆加载、LLM 结构化生成、校验、人工中断、指标生成和持久化。
5. MySQL 在事务中同步元数据快照和被接受的长期记忆。
6. worker 把检查点状态投影到安全的 Redis 公开任务状态，并通过 cleanup outbox 删除终态检查点。

每一步都要交叉核对模型、存储、错误处理和测试，不以文件注释代替行为验证。

## 6. To-Be 设计方法

To-Be 不以认证、多租户、计费或运营后台为中心。目标设计通过以下步骤形成：

1. 从 As-Is 事实提取模块耦合、职责重叠、状态一致性、扩展点和测试边界。
2. 区分已经合理的约束与需要演进的问题，避免为了“架构感”而增加层次。
3. 给出一套推荐的目标模块和依赖方向。
4. 对关键争议点提供少量备选方案并做出明确推荐。
5. 把目标拆成可独立验证的演进阶段，不要求本任务实施。

To-Be 至少回答：

- API、应用服务、领域/工作流、持久化和基础设施边界如何收敛。
- Redis 公开任务投影、调度状态和 LangGraph 检查点如何保持清晰职责。
- 外部检索与嵌入能力何时进入主路径，以及如何通过端口隔离。
- 工作流版本、提示版本、数据版本和迁移兼容如何治理。
- 可观测性、故障恢复和契约测试如何随架构演进。

## 7. 兼容性与回滚

- 任务只写文档，没有运行时兼容性风险。
- README 仅增加入口链接。
- 若某项架构结论无法从仓库确认，应降级为“推断/待确认”或删除。
- 若 To-Be 建议缺乏当前技术问题支撑，应移出推荐架构而不是扩大范围。
- 回滚只需移除新增文档和 README 入口，不触及代码或数据。
